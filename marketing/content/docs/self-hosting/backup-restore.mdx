title: Backup & restore
description: "Complete instance backup: database plus attachments, for SQLite or PostgreSQL."

> **Current TradeLens status:** official TradeLens GHCR images are published. `make up` (SQLite) and `make up-postgres` (PostgreSQL) use them by default. Source-build fallback remains available through `make up-build` / `make up-postgres-build`. Docker publisher and Release Please remain `disabled_manually`; image availability does not imply continuous publishing is enabled.
>
> **Database boundary:** TradeLens and upstream TraderMemos migration histories have diverged. Never hand a database used by one product to the other, including PostgreSQL. Use separate projects and fresh databases for different products. Switching an existing TradeLens source deployment to official TradeLens images is a same-product deployment change: take a complete backup, then preserve the checkout, Compose project, configuration and volumes.

A full-instance backup requires **SQLite database + attachments**, or **PostgreSQL database dump + attachments**. Attachment and note-media metadata is in the database; restoring only one side leaves broken references. Securely preserve `.env`, secrets, the source commit and Compose configuration separately so you can recreate the same installation. Customized database or `TM_ATTACH_DIR` paths must also be included.

## Account exports are not instance backups

Account ZIP exports contain `export.json` and exported account attachments. JSON/CSV exports cover selected trading data. Research Markdown exports are research records. None is a complete instance backup: they do not recreate all users, authentication, server settings and all instance data. Use exports for account portability or research; use the database and attachment procedures below for instance recovery.

## SQLite: stop writes and archive the data volume

The default `tm_data` volume contains `/data/tradermemos.db` and `/data/attachments`. SQLite uses WAL: stop the API and archive the whole `/data` directory, including any WAL files. Keep the API stopped until backup finishes. These commands assume default paths and the existing Compose project.

```bash
docker compose stop api
docker run --rm --volumes-from "$(docker compose ps -aq api)" -v "$PWD":/backup alpine \
  tar czf /backup/tradelens-data.tar.gz -C /data .
docker compose start api
```

## SQLite restore

Use a separate fresh host/project, the same TradeLens image version and configuration, and an empty destination volume. Pull and create containers without starting the API, extract the archive, then start. Do not overwrite a running instance or an upstream database. Retain the original backup and verify login, account data and attachments after restore.

```bash
docker compose -f docker-compose.yml pull
docker compose -f docker-compose.yml create
docker run --rm --volumes-from "$(docker compose ps -aq api)" -v "$PWD":/backup alpine \
  tar xzf /backup/tradelens-data.tar.gz -C /data
make up
```

## PostgreSQL: dump + attachments

The PostgreSQL overlay stores the database in `tm_pg_data` and attachments in `tm_data`. Stop the API (and any other writers) throughout the dump and attachment archive so both represent the same state. Use both Compose files for every command; the base Compose file alone does not define `postgres`.

```bash
docker compose -f docker-compose.yml -f docker-compose.postgres.yml stop api
docker compose -f docker-compose.yml -f docker-compose.postgres.yml exec -T postgres pg_dump -U tm tradermemos > tradelens-db.sql
docker run --rm --volumes-from "$(docker compose -f docker-compose.yml -f docker-compose.postgres.yml ps -aq api)" -v "$PWD":/backup alpine \
  tar czf /backup/tradelens-attachments.tar.gz -C /data attachments
docker compose -f docker-compose.yml -f docker-compose.postgres.yml start api
```

## PostgreSQL restore

Use a separate fresh project with the same image version/configuration and empty volumes. Start only PostgreSQL, restore the dump into its empty database and restore the attachment archive before starting the API. Do not restore a SQLite archive as a PostgreSQL database. Verify accounts and attachments; keep backups offsite and test recovery before relying on them.

```bash
docker compose -f docker-compose.yml -f docker-compose.postgres.yml pull
docker compose -f docker-compose.yml -f docker-compose.postgres.yml create
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d --wait postgres
docker compose -f docker-compose.yml -f docker-compose.postgres.yml exec -T postgres psql -v ON_ERROR_STOP=1 -U tm -d tradermemos < tradelens-db.sql
docker run --rm --volumes-from "$(docker compose -f docker-compose.yml -f docker-compose.postgres.yml ps -aq api)" -v "$PWD":/backup alpine \
  tar xzf /backup/tradelens-attachments.tar.gz -C /data
make up-postgres
```

For source-build recovery, add `-f docker-compose.build.yml` immediately after the base
file on every Compose command, use `build` instead of `pull`, and start with
`make up-build` / `make up-postgres-build`. Restore before API startup so the
selected version can check/run migrations normally. Retain deployment secrets separately.

## Scheduled SQLite snapshots

SQLite takes daily database snapshots by default, keeping 14. Owners can view failures
and trigger **Back up now** in Settings → About → Backups. `TM_BACKUP_ENABLED=false`,
`TM_JOBS_ENABLED=false` or `TM_BACKUP_INTERVAL_MIN=0` disables the schedule; manual
backup still works. `TM_DEMO_MODE=true` disables both. PostgreSQL uses pg_dump above.

`TM_BACKUP_DIR` defaults to `<dbDir>/backups` (Docker `/data/backups`). The persistent
`<database>.backup-id` sidecar selects an isolated `tradelens-<database-id>/` directory.
Retain that identity with the database volume. Only matching snapshots in that directory
are pruned; other instances remain untouched even when containers use identical paths.
Use persistent local storage with advisory locks, atomic rename and fsync. Sync offsite;
ephemeral Render storage is not a recoverable backup. Snapshots contain the database only;
retain attachments and configuration/secrets separately.

Restore drill: preserve a rollback copy, stop all API replicas, copy a selected snapshot
over the configured database, remove its stale `-wal` and `-shm`, restore matching
attachments/secrets, run SQLite `PRAGMA integrity_check` and expect `ok`, then start the
same TradeLens version and verify login, accounts, trades and attachment read-back.
Never mix upstream TraderMemos and TradeLens databases. The full-volume archive procedure
above remains available. See [deployment details](https://github.com/HoesenBruce/TradeLens/blob/main/docs/deploy.md#backups--restore).
